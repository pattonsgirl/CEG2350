# Linux I/O Streams: Exercise Set

>| Generated by Claude

A hands-on progression through the three standard streams (stdin, stdout, stderr),
redirection, and piping. Do each exercise in a terminal — don't just read them.

Every process starts with three open file descriptors:

| FD | Name   | Number | Default destination |
|----|--------|--------|----------------------|
| stdin  | standard input  | 0 | keyboard |
| stdout | standard output | 1 | terminal |
| stderr | standard error  | 2 | terminal |

Redirection reassigns where these descriptors point. Piping connects one
process's stdout directly to another process's stdin.

## Setup

Run this once to create a sandbox with some files to play with:

```bash
mkdir ~/stream-lab && cd ~/stream-lab
printf "banana\napple\ncherry\napple\ndate\n" > fruits.txt
printf "3\n1\n4\n1\n5\n9\n2\n6\n" > numbers.txt
mkdir -p secret   # a dir we deliberately can't read into as a file
```

All exercises below assume you're in `~/stream-lab`.

## Part 1 — Output Redirection (`>` and `>>`)

**1.1** Redirect the output of `ls` into a file called `listing.txt`, then
view the file with `cat`.

**1.2** Run `echo "hello"` twice, redirecting into `listing.txt` both times
with `>`. Check the file — what happened to the first line?

**1.3** Now do the same but use `>>` the second time. What's different?

**1.4** Predict, then verify: what does this do?

```bash
echo "line one" > out.txt
echo "line two" > out.txt
echo "line three" >> out.txt
cat out.txt
```

**1.5** Challenge: without using `cp`, use redirection alone to duplicate
`fruits.txt` into `fruits_copy.txt`.

<details>
<summary>Hints / Answers — Part 1</summary>

- `>` **truncates** the file first — it always starts writing from byte 0,
  destroying prior contents. `>>` **appends** to the end.
- 1.5: `cat fruits.txt > fruits_copy.txt`
- Common trap: `sort fruits.txt > fruits.txt` looks reasonable but silently
  destroys the file — the shell truncates `fruits.txt` (via `>`) *before*
  `sort` ever reads it, so `sort` reads an empty file. This is why you
  redirect into a *different* file, or use a temp file + `mv`.

</details>

## Part 2 — Input Redirection (`<`)

**2.1** Instead of `cat fruits.txt`, feed the file to `cat` using `<`
redirection: `cat < fruits.txt`. Note the output looks identical — but
think about *why* the mechanism is different (argument vs. stdin).

**2.2** Sort `numbers.txt` numerically using input redirection instead of
passing it as an argument:

```bash
sort -n < numbers.txt
```

**2.3** Use `wc -l < fruits.txt` and separately `wc -l fruits.txt`. Compare
the output. Why does one show a filename and the other doesn't?

**2.4** Combine input and output redirection in a single command: read from
`numbers.txt`, sort it numerically, and write the result to `sorted.txt`.

<details>
<summary>Hints / Answers — Part 2</summary>

- 2.1: `cat fruits.txt` passes the filename as an *argument* — `cat` opens
  the file itself. `cat < fruits.txt` instead connects the file to `cat`'s
  stdin, and `cat` just copies stdin to stdout, never knowing a filename
  was involved.
- 2.3: when you give `wc` a filename argument, it knows the name and prints
  it alongside the count. When you redirect via `<`, `wc` only ever sees an
  anonymous stream of bytes on stdin, so it can't print a name.
- 2.4: `sort -n < numbers.txt > sorted.txt`

</details>

## Part 3 — Piping (`|`)

A pipe connects the stdout of one command directly to the stdin of the
next — no intermediate file.

**3.1** Count how many lines are in `fruits.txt` using a pipe instead of a
redirect: `cat fruits.txt | wc -l`. (This is a classic "useless use of
cat" — see the reflection question below.)

**3.2** Find the unique fruits in `fruits.txt`, sorted, with counts. Chain
three commands: `sort`, `uniq -c`, on `fruits.txt`.

**3.3** From `numbers.txt`, get the *largest* number using a pipe chain
(`sort -n`, then something to get the last line).

**3.4** Build a 4-stage pipeline: list files in `/etc` (`ls /etc`), keep
only lines containing the letter `c` (`grep c`), sort them, and show only
the first 5 (`head -5`).

**3.5** Reflection: `cat fruits.txt | wc -l` vs. `wc -l < fruits.txt` vs.
`wc -l fruits.txt` all print the same number. Explain in one sentence what's
happening differently at the process level in each case (how many processes
are started, and how data physically moves between them).

<details>
<summary>Hints / Answers — Part 3</summary>

- 3.2: `sort fruits.txt | uniq -c`
- 3.3: `sort -n numbers.txt | tail -1`
- 3.4: `ls /etc | grep c | sort | head -5`
- 3.5: `cat fruits.txt | wc -l` starts **two** processes (`cat`, `wc`)
  connected by an in-memory pipe — wasteful since `wc` could open the file
  itself. `wc -l < fruits.txt` and `wc -l fruits.txt` each start **one**
  process; the difference is only *how* `wc` obtains the bytes (its own
  `open()` call vs. an inherited, pre-opened file descriptor from the
  shell).

</details>

## Part 4 — stdout vs. stderr

Programs write normal output to stdout (fd 1) and error/diagnostic output
to stderr (fd 2). By default both land on your terminal, which is why they
look the same — until you start redirecting.

**4.1** Run this and observe both lines print to the terminal:

```bash
ls fruits.txt nonexistent.txt
```

**4.2** Now redirect *only* stdout to a file: `ls fruits.txt nonexistent.txt > out.txt`.
What appears on your terminal? What ends up in `out.txt`?

**4.3** Now redirect *only* stderr: `ls fruits.txt nonexistent.txt 2> err.txt`.
What's on screen now, and what's in `err.txt`?

**4.4** Send stdout to one file and stderr to a different file, in a single
command:

```bash
ls fruits.txt nonexistent.txt > out.txt 2> err.txt
```

Inspect both files.

**4.5** Send stdout AND stderr to the *same* file. Try this, then explain
why it's subtly wrong:

```bash
ls fruits.txt nonexistent.txt > both.txt 2> both.txt
```

(Hint: run it, check `both.txt` — sometimes it looks fine, sometimes lines
get clobbered or interleaved oddly. The two redirections open the file
independently, each with their own file position.)

**4.6** Now do it the *correct* way, using `2>&1`:

```bash
ls fruits.txt nonexistent.txt > both.txt 2>&1
```

Explain why **order matters** here — `2>&1 > both.txt` (order reversed)
does *not* do the same thing. Try it and see where stderr ends up.

**4.7** Discard stderr entirely (silence errors) by sending it to the null
device: `ls fruits.txt nonexistent.txt 2> /dev/null`.

**4.8** Discard *both* streams — run a command with no output at all
reaching your terminal.

**4.9** Challenge: write one command that runs `ls` on both a real and a
fake file, shows normal output on the terminal as usual, but silently
swallows only the error.

<details>
<summary>Hints / Answers — Part 4</summary>

- 4.2: The error line (from `ls`) still prints to your terminal, since only
  stdout was redirected. `out.txt` contains just the successful listing
  line.
- 4.3: The normal listing still prints to your terminal; `err.txt` contains
  just the "No such file" message.
- 4.5: Both redirections open `both.txt` *independently* (two separate file
  descriptors, each starting their own write position at the truncated
  start). Depending on timing/buffering, output can overwrite or interleave
  unpredictably. It "often looks right" for simple cases like this one
  purely by luck, which makes it a dangerous habit.
- 4.6: `2>&1` means "make fd 2 point to wherever fd 1 currently points."
  Redirections are processed **left to right**. In
  `> both.txt 2>&1`: first stdout is pointed at `both.txt`, *then* stderr is
  pointed at "wherever stdout currently is" (`both.txt`) — so both correctly
  share one fd/file. In `2>&1 > both.txt`: stderr is first pointed at
  "wherever stdout currently is" (the terminal), *then* stdout is redirected
  to `both.txt` — stderr keeps going to the terminal instead of the file.
- 4.7 / 4.8: `/dev/null` is a special file that discards anything written to
  it. `command > /dev/null 2>&1` discards both.
- 4.9: `ls fruits.txt nonexistent.txt 2> /dev/null`

</details>

## Part 5 — Combining Everything

**5.1** Run a command that deliberately errors (e.g. `grep xyz nonexistent.txt`),
pipe its stdout into `wc -l`, and separately redirect its stderr to
`error.log`. (Two different destinations, one command.)

**5.2** Build a pipeline that: reads `numbers.txt`, sorts it numerically,
removes duplicates, and **appends** the result to a running log file
`history.log` — without ever overwriting previous runs.

**5.3** Use `tee` to solve a problem pure redirection can't: sort
`fruits.txt` and simultaneously (a) show the result on your terminal and
(b) save it to `sorted_fruits.txt`. (Look up `man tee` if you haven't used
it — its whole purpose is "duplicate a stream.")

**5.4** Extend 5.3: same as above, but append instead of overwrite
`sorted_fruits.txt` (`tee` has a flag for this).

**5.5** Capstone: write a single pipeline that finds all `.txt` files in
the current directory (`ls *.txt`), for each one greps for lines containing
the letter `a` (you'll need `cat *.txt | grep a` or `grep a *.txt`), counts
the total matching lines, and writes that count to `count.txt` — while any
errors from the whole pipeline go to `errors.log` instead of your screen.

<details>
<summary>Hints / Answers — Part 5</summary>

- 5.1: `grep xyz nonexistent.txt 2> error.log | wc -l`
- 5.2: `sort -n numbers.txt | uniq >> history.log`
- 5.3: `sort fruits.txt | tee sorted_fruits.txt`
- 5.4: `sort fruits.txt | tee -a sorted_fruits.txt`
- 5.5: `grep a *.txt 2> errors.log | wc -l > count.txt`

</details>

## Quick Reference

| Syntax | Meaning |
|---|---|
| `cmd > file` | stdout → file (truncate/overwrite) |
| `cmd >> file` | stdout → file (append) |
| `cmd < file` | file → stdin |
| `cmd1 \| cmd2` | stdout of cmd1 → stdin of cmd2 |
| `cmd 2> file` | stderr → file |
| `cmd 2>> file` | stderr → file (append) |
| `cmd > file 2>&1` | stdout and stderr → same file |
| `cmd &> file` | stdout and stderr → same file (bash shortcut) |
| `cmd > /dev/null 2>&1` | discard all output |
| `cmd \| tee file` | stdout → both terminal and file |
| `cmd \| tee -a file` | stdout → both terminal and file (append) |

**Rule of thumb for `2>&1` order:** redirections apply left-to-right, so
put `2>&1` *after* the stdout redirect it's supposed to follow.
